Vowbase iOS · design review

Two screens to judge before we build.

The inline-edit affordance and the comparison grid are the two decisions in the Venues spec that are much easier to argue about as pictures. Everything below is drawn in Vowbase's own tokens — rose #C22659, blush, New York for names, SF for everything else — so what you're judging is the app, not a mockup style. The three questions this board opened are now closed; the answers are at the foot.

Plate 1

Venue Detail — read, then editing in place

Same screen, two states. Nothing modal happens between them: the capacity cell's label is replaced by a field with the identical frame, and the rest of the screen stays live and legible.

  1. 4.2

    The field replaces the label in place. Same font, same baseline, same leading — the row must not shift by a pixel when it flips. Selection is "all" so overtyping replaces. The only new chrome is a 1 pt rose underline.

  2. 4.2

    The screen stays live. No dimming, no scrim, no modal. You can read the notes while you fix the capacity. This is the entire argument for inline over a form sheet.

  3. 4.3

    Saving is a 2 pt hairline under the nav bar — never a per-row spinner, which would make the row jump. On failure the row reverts with a rose flash and grows a one-line Couldn't save — Retry caption.

  4. 3

    Unset fields are visible, not absent. Add all-in est. and Add email are muted rows, not gaps. Today the whole Details section vanishes when every contact field is nil, which leaves no route to ever set them.

  5. 4.4

    Notes is the one place we show save state. Saved · 2 min ago, because it's the one field where losing input would actually hurt. Autosaves on a 2 s idle timer, on blur, and on backgrounding.

  6. 4.6

    Location is the one field that can't be a plain text box. Editing it opens inline autocomplete; committing a typed string with nothing selected clears the coordinates and the row grows a muted Not on map caption — so the tradeoff is visible at the moment it's made, not the next time you open the Map tab.

Settled: no edit glyph on any row — a pencil would imply the rows without one aren't editable. Discoverability rests on the muted Add … rows, a highlight on touch-down, and VoiceOver's button trait. If first-run testing says people don't find it, the fix is a one-time coach mark, not permanent chrome on every row.

Plate 2

Compare — pinned attributes, paging venue columns

The current sheet stacks venues vertically, so you can never see two capacities at once — which is the whole job. Here the attribute column is pinned and the venue columns page horizontally, with the third always peeking so the gesture is discoverable.

  1. 9.2

    Row height is uniform across columns — the tallest cell sets it. That single constraint is what makes the grid scannable and is exactly what the stacked list can't do.

  2. 9.2

    The dot marks best-in-row on three attributes only: lowest venue estimate, largest capacity ceiling, shortest guest travel. Nothing subjective gets a marker — we are not scoring the light at 5pm.

  3. 10.4

    Guest travel is currently a hardcoded string ("Unavailable" in ContentView). Until it's wired from the map repository this row reads Not available and is excluded from the dot logic — never a dash that reads as zero.

  4. 9.2

    Not added stays visible. An empty cell would read as "cheap" or "small." Naming the gap is what makes the couple go find the number.

  5. 9.3

    Above accessibilityMedium the grid stops working at any column width. At that threshold it flips to one card per attribute with all venues listed inside — so the comparison survives even though the grid doesn't.

  6. 9.1

    Getting here: a floating bar above the tab bar reading 2 selected · Clear · Compare, not the inline button that scrolls away. The 4th selection gets a caption, not just a haptic nobody can feel.

Judge this: two columns at 130 pt each is tight for money and time strings at larger type. The alternative is one venue per page with the attribute column pinned — safer, but it stops being a comparison and becomes a flipbook. I'd hold the two-column floor.

Settled — 30 July 2026

Notes live in our_notes

The web client settles it

The web Venues pane reads venue.our_notes and writes our_notes: v || null under a section labelled Our notes; bare notes is never read there at all. A July 2026 migration had already backfilled our_notes = notes. So notes is legacy, not research — iOS mirrors the web exactly and stops displaying it. An earlier draft of the spec proposed surfacing it in a From research section; that's dropped, and so is the migration warning that came with it.

Fields can be cleared

VenuePatch adopts NullablePatch

Optionals encoded with encodeIfPresent make nil mean "don't touch," with no way to express NULL — so today a website you set is a website you're stuck with. GuestPatch already solved this; venues take the same type. The web app clears with exactly these semantics (v || null), so this lines the two clients up rather than inventing anything. Every muted Add … row in Plate 1 depends on it.

No glyph, on any row

The pencil is out

Marking one row as editable implies the unmarked ones aren't, which inverts the rule the whole screen runs on. Discoverability moves to the Add … rows, a touch-down highlight, and the VoiceOver button trait — none of which were ever carrying the glyph's weight anyway.
